# E15d — 탭 드래그 떼어내기

> E15c 스펙 §7의 분리분. 사용자 확정: "드래그까지 전부"(2026-08-10).
> 탭을 끌어 ① 창 밖에 놓으면 새 창 ② 다른 창의 탭바에 놓으면 그리로 이동 ③ 같은 탭바 안에서는 순서 변경.

## 1. 미지수와 설계 — 창 밖 pointerup

E15c 스펙이 "창 밖 `pointerup` 수신 여부"를 미지수로 남겼다. **설계로 우회한다**:

- 탭 버튼이 `pointerdown`에서 **`setPointerCapture(pointerId)`** — Chromium은 캡처한 요소에
  버튼을 놓을 때까지 `pointermove`/`pointerup`을 전달한다(**창 밖 좌표 포함** — 표준 동작이나
  실측 확인 대상). 렌더러는 이벤트의 `screenX/screenY`를 main에 중계한다.
- main은 **커서를 직접 추적하지 않는다** — 렌더러가 중계한 스크린 좌표로 드롭 대상을 판정한다.
  main이 필요로 하는 것은 `tab-drag:move(screenX, screenY)`와 `tab-drag:end(screenX, screenY)` 둘뿐.
- **CDP로 전 배선이 검증 가능**하다: 합성 이벤트에 임의 screen 좌표를 실을 수 있다.
  잔여 위험은 "실제 OS에서 캡처가 창 밖까지 전달되는가" 하나 — **관문 태스크에서
  숨김 창 + CDP 합성으로 배선을 검증하고, 실기기 확인 1회는 병합 후 사용자 실사용 몫으로
  명시한다**(E2E 창 절대 금지 룰 — 보이는 프로브는 하지 않는다).

## 2. 동작

| 드롭 위치 | 결과 |
| --- | --- |
| 같은 탭바 안 | **순서 변경** — `registry.moveTab(windowId, tabId, toIndex)` + 뷰 무변(가시성만 유지) |
| 다른 창의 탭바 영역(스크린 좌표로 판정) | **탭 이동** — 뷰를 `removeChildView` 후 대상 창 `addChildView`. webContents 그대로(직렬화 불요 — E15c가 놓은 토대) |
| 그 외(창 밖) | **새 창** — 커서 위치에 창 생성, 뷰 이동. 마지막 탭이었으면 원래 창은 닫힘 |

- 드래그 중 시각: **끌리는 탭의 고스트는 그리지 않는다**(1차 범위 — 커서만). 드롭 예상 위치
  표시(탭바 삽입선)는 같은 창 안 순서 변경에만 그린다(렌더러 로컬이라 값싸다).
- 임계값: `pointerdown` 후 4px 이동부터 드래그(클릭과 구분 — 기존 탭 클릭·⌥클릭 무변).
- ESC로 드래그 취소.

## 3. 경계·보안

- `tab-drag:*`의 `tabId`는 렌더러 입력 — **자기 창의 탭만**(E15c `tabs:activate` 관례).
- 이동 대상 창 판정은 main이 레지스트리+`getBounds()`로 한다 — 렌더러가 창 id를 지정하지 않는다.
- 드래그 중 그 탭이 크래시하면(E15e) 드래그를 취소한다.
- 이동 후 감시·터미널·설정은 **자동으로 따라간다** — 전부 `webContents.id` 키라 창 소속과 무관.
  단, **레이아웃은 창 단위**(E15c §4)라 이동한 탭은 새 창의 layout을 받아야 한다(push 1회).

## 4. 하지 않는 것

- 드래그 고스트 이미지·창 사이 삽입선(1차 범위 밖) · 다중 선택 드래그 · 탭 복제

## 5. 성공 기준

- 같은 탭바 순서 변경·다른 창 이동·창 밖 새 창이 CDP 합성으로 E2E 검증된다
- 이동한 탭의 감시·터미널이 계속 살아 있다(webContents 유지의 실증)
- 기존 클릭·⌥클릭·우클릭이 그대로다(임계값 미만 무변)
- 게이트: lint 0 · 6/6 · 713 이상 · e2e 168 이상 · **E2E 중 창 절대 안 보임**(하네스 불변식)

## 실행 중 실측 정정 (Task 1 관문)

- **합성 이벤트의 `screenX/screenY`는 창 상대 좌표다**(CDP 실측 — 창 bounds (360,84)에서 `event.screenX === clientX`). §1의 "이벤트의 screenX/screenY를 중계"는 그대로 쓰면 안 되고, 렌더러가 **`clientX + window.screenX`로 절대 좌표를 계산해 중계**한다. 실 OS 입력에서는 두 식이 같은 값(뷰가 창 원점 전체 크기)이라 프로덕션 의도는 불변. macOS hidden 타이틀바에서 `contentBounds == bounds` 실측.
- **캡처는 CDP 합성에서 창 밖 좌표까지 전달된다**(-50,-40 · 2000,17 → 캡처 요소로 재타게팅). 잔여 위험은 실 OS 확인 1회뿐(§1 명시대로 병합 후 실사용 몫).
- **드래그 뒤 click이 캡처 요소에서 여전히 발화한다** — 잔여 클릭 억제(`suppressClickRef`)가 필수(실측으로 확인).
- **`tab-drag:end`는 4-인자다**: `(tabId, screenX, screenY, toIndex)` — 탭 픽셀 배치는 DOM 몫이라 main이 toIndex를 계산할 수 없다. 렌더러가 삽입선용으로 이미 계산하는 값이고, main은 자기 창 탭바 영역일 때만 쓰며 레지스트리가 클램프한다.
