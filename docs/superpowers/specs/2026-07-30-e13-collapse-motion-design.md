# E13 — 접기 모션 설계

2026-07-30 사용자 피드백: "애니메이션같은건 없어? 너무 딱딱한데.."

E12의 사이드 접기와 E7b의 터미널 도크 열고 닫기가 **즉시 튄다.** 사용자 선택: **사이드 + 터미널 도크**.

## 이건 내가 막아 둔 것이다

E11 스펙이 "레이아웃 속성은 애니메이션하지 않는다"를 규칙으로 세웠고, E12 플랜에서 내가 **"접기/펼치기는 전환하지 않는다"고 명시적으로 지시**했다. 근거는 "열 폭은 인라인 style이고 레이아웃 속성이라 전환하면 버벅인다"였다.

**원칙은 맞지만 이 경우엔 과했다.** E11 스스로 예외를 하나 만들어 두었다 — 상세 슬롯은 `grid-template-rows`로 부드럽게 열린다(Chromium이 보간하는 몇 안 되는 레이아웃 경로). **같은 기법이 열에도 그대로 적용되는데** 내가 "레이아웃 = 금지"로 일반화하면서 그 연결을 놓쳤다. 안전망도 `grid-template-rows`만 허용하고 `grid-template-columns`는 금지 목록에 넣어 두어(`motion-tokens.test.ts:51`) 이 길을 스스로 막았다.

## 실측 — 왜 단순 전환으로는 안 되는가

**① 접힌 열이 언마운트된다.** `App.tsx:270-272`는 접히면 트랙 문자열에서 그 열을 **아예 뺀다**(`leftCollapsed ? null : '${columns.left}px'`)고, 열 자체도 조건부 렌더다. 없어진 것에서 전환할 수는 없다 — E11이 상세 슬롯에서 똑같이 겪고 래퍼를 항상 렌더해 푼 문제다.

**② `gap`이 트랙과 무관하게 계산된다.** E11 Task 4가 실측으로 배운 그 함정이다: CSS grid의 `gap`은 트랙이 `0`이어도 **무조건** 자리를 차지한다. `.app__main`은 `gap: var(--space-4)`(16px)에 열이 최대 4개(좌·중앙·리사이저·우)라 gap 3개 = 48px, 리사이저 6px. **트랙만 0으로 만들면 접어도 54px이 남는다.**

E11은 그때 `gap`을 없애고 조건부 `margin-bottom`으로 옮겼는데, 최종 리뷰가 **"첫 프레임에 22.5px이 튄다"**고 지적했다(240ms 중 첫 프레임에 계단, 나머지가 부드러운 보간). 감수한 타협이었지만 **여기서 반복하면 안 된다** — 열 방향은 gap이 3개라 계단이 최대 48px이 된다.

**③ 도크는 `display: none`이다.** `App.tsx:1109`가 `display: dockOpen ? 'block' : 'none'`으로 껐다 켠다. `display`는 보간되지 않으므로 이것도 구조를 바꿔야 한다.

## ① 간격을 트랙으로 — 접기 모션의 핵심

`.app__main`의 `gap`을 **0으로 만들고 간격을 `grid-template-columns` 안의 트랙으로 표현**한다. 그러면 열·간격·리사이저가 **하나의 속성**이 되어 함께 보간되고, ②의 계단이 원천적으로 사라진다.

```
지금:  gap: 16px,  columns = [좌] [중앙] [6px] [우]
바꿈:  gap: 0,     columns = [좌] [16] [중앙] [16] [6] [16] [우]
접힘:  gap: 0,     columns = [0]  [0]  [중앙] [16] [6] [16] [우]
```

- **접힌 열은 트랙을 지우지 않고 `0`으로 둔다.** 그 열은 `overflow: hidden`으로 계속 마운트돼 있어야 전환의 시작점이 존재한다.
- 전환은 `grid-template-columns`에 `--motion-slow`(240ms) `--ease-in-out` — 상세 슬롯과 같은 값이라 앱 안에서 "크게 열리고 닫히는 것"의 속도가 하나로 통일된다.
- **`computeColumns`는 그대로 쓴다.** 이미 접힘을 입력으로 받고 트랙 수에 따라 크롬을 재계산한다(E12). 바뀌는 건 결과를 **어떤 문자열로 조립하느냐**뿐이다.

## ② 도크 열고 닫기

`display: none` → **행 트랙 전환**. `.app__main`은 이미 `grid-template-rows: minmax(0,1fr) auto`이므로 두 번째 행을 `0fr ↔ auto`가 아니라 **`0px ↔ <높이>px`**로 두고 전환한다(`auto`는 보간되지 않는다 — 도크 높이는 이미 `terminalHeight` 설정으로 px를 알고 있다). 도크는 `overflow: hidden`으로 유지 마운트.

⚠️ **행 gap도 같은 문제**를 갖는다 — `.app__main`의 `gap`이 행에도 걸리므로, ①에서 `gap: 0`으로 만들 때 **행 간격도 트랙으로** 옮겨야 한다.

## ③ 무엇을 계속 금지할 것인가

`grid-template-columns`를 안전망 허용 목록에 **추가**하되, **`.app__main`이라는 좁은 용도로만** 쓰이도록 주석으로 못박는다. `height`·`width`·`margin`·`padding` 금지는 그대로다 — 이번에 푸는 것은 "grid 트랙은 Chromium이 보간하는 예외 경로"라는 **이미 확립된 예외의 확장**이지, 원칙의 철회가 아니다.

## 에러·엣지

| 상황 | 처리 |
| --- | --- |
| 접힌 열 안의 가상 스크롤 | 좌측 `ChangesPanel`·우측 `HistoryPanel`이 240ms 동안 폭이 변한다 → 매 프레임 재측정. **E11이 행 방향에서 검증한 것과 같은 계열이지만 폭 방향은 처음이다 — 프레임별 실측 필수.** 깨지면 접힘 모션을 포기하고 도크만 남긴다 |
| 접힘 상태 복원(앱 시작) | 시작 시엔 **전환하지 않는다.** 첫 페인트에 240ms 애니메이션이 도는 건 부팅이 느려 보이는 것과 구별되지 않는다 — 초기 렌더에 전환 억제 클래스를 씌우고 첫 프레임 뒤 푼다(E11 테마 억제와 같은 기법) |
| 드래그 리사이즈 | **전환을 타면 안 된다.** 드래그 중에는 커서를 1:1로 따라가야 한다(E11 스펙의 판단 그대로). 드래그 동안 전환을 끈다 |
| 창 리사이즈 | 같은 이유로 전환 금지. 창을 끌 때 열이 뒤따라오면 고무줄처럼 보인다 |
| `prefers-reduced-motion` | E11의 전역 차단이 이미 덮는다(`transition-duration: 0.01ms !important`) — 새로 할 일 없음. 확인만 |
| E2E 폭 단언 | 240ms 동안 폭이 중간값이라 즉시 단언하면 흔들린다. **E12의 ⌘F 플레이크가 정확히 이 원인이었다** — 자동 재시도 단언으로 최종값을 기다리게 하고, 고정 대기를 넣지 않는다 |
| 도크 높이 드래그 중 열림 전환 | 두 전환이 겹치지 않게 — 높이 드래그 중에는 행 전환도 끈다 |

## 테스트

- **순수 단위**: 트랙 문자열 조립 함수(`buildMainColumns(columns, collapse)` — 접힘·펼침·양쪽 접힘에서 트랙 개수와 합이 기대와 같은지). gap을 트랙으로 옮기면 **합계가 창 폭과 맞아야 한다**는 불변식을 테스트로 고정한다.
- **E2E**: ① 접기 후 최종 폭이 E12와 동일(**전환이 끝난 뒤**를 단언) ② 도크를 닫으면 중앙이 그만큼 커진다 ③ `prefers-reduced-motion`에서 즉시 반영된다.
- **무회귀**: E12 접기 5건·E6a 열 폭·E7b 도크·E11 상세 슬롯 전건(113).
- **실측 보고**: 접히는 240ms 동안 (a) 프레임 드랍 (b) 가상 스크롤 행이 깨지는지 (c) 시작 시 전환이 돌지 않는지.
- **스크린샷**: 접히는 중간 프레임(모션은 정지 이미지로 안 보인다 — E11 관례).
