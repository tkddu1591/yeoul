# E15c — 앱이 직접 그리는 탭바 (한 창에 저장소 여러 개)

> 사용자 요구: **"인텔리처럼 여러개 선택해서 여러개 창 띄우거나 탭으로 관리하거나"**
> E15a가 저장소 전환을, E15b가 여러 창을 했다. **탭이 마지막 조각이다.**
> E15b는 네이티브 탭으로 하려다 **구현 불가**로 닫혔다 — `titleBarStyle: 'hidden'`이
> AppKit 수준에서 탭을 금지한다(실측). 그래서 앱이 직접 그린다.

## 1. 사용자 결정 (이 브레인스토밍에서 확정)

| 물음 | 답 |
| --- | --- |
| 탭이 뭘 해 줘야 하나 | **둘 다** — 한 창에 여러 저장소 + 여러 창도 계속. 비용은 감수한다 |
| 탭바 배치 | **두 줄** — 탭바가 타이틀바를 겸하고 헤더는 그 아래 |
| 사이드 접힘·폭·터미널 높이 | **창 안에서 같다** (탭마다 따로가 아니다) |
| 떼어내기 | **드래그까지 전부** |

## 2. 창 모델을 바꾼다

지금은 `BrowserWindow` 하나 = 저장소 하나다. 이걸 바꾼다:

```
BaseWindow (titleBarStyle: 'hidden', trafficLightPosition)
└─ contentView
   ├─ WebContentsView(git-gui)      ← 활성. y=0..height 전체
   ├─ WebContentsView(api-server)   ← setVisible(false)
   └─ WebContentsView(design)       ← setVisible(false)
```

**실측(Electron 35.7.5)**: `BaseWindowConstructorOptions`에 `titleBarStyle`(`electron.d.ts:231`)과 `trafficLightPosition`(`:237`)이 있다 — **한 줄 타이틀바를 지키면서 탭을 만들 수 있다.** E15b에서 막혔던 것이 여기선 안 막힌다. `WebContentsView`(`:17434`) · `contentView`(`:1462`) · `addChildView` · `setBounds` · `setVisible` 전부 존재.

### 탭바는 각 뷰가 자기 안에 그린다

**별도 `WebContentsView`로 두지 않는다.** 그러면 창마다 webContents가 하나 더 생겨 Playwright의 `firstWindow()`가 무엇을 돌려줄지 모호해지는데, **`smoke.spec.ts`에 `firstWindow()`가 155곳 있다**(실측). 탭바를 각 저장소 뷰가 그리면 webContents 수 = 탭 수이고 `firstWindow()`는 여전히 저장소 뷰를 돌려준다.

- 탭 목록은 main이 그 창의 **모든 뷰에 push**한다(`repo:changed`와 같은 관용구)
- 탭 클릭은 main이 `setVisible`을 바꿔 답한다
- 숨은 뷰가 탭바를 중복 렌더하지만 `setVisible(false)`면 페인트하지 않는다

### E15b의 산출물이 거의 그대로 산다

레지스트리·감시 `Map`·터미널 `targets`·설정 분리가 전부 `sender.id` 기준인데, **이제 그것이 창이 아니라 탭을 가리킨다.** 키의 의미만 바뀌고 배선은 그대로다. 터미널 상한 8도 자동으로 **탭마다 8개**가 된다.

`window-registry`만 한 겹 깊어진다:

```ts
interface WindowState {
  /** webContents.id — 배열 순서가 곧 탭 순서 */
  tabs: number[]
  activeTab: number
  /** 창 단위 (§4) */
  layout: WindowLayout
}
/** 탭 → 저장소. 지금 WindowState.repoPath가 하던 일이 이리로 내려온다 */
interface TabState {
  repoPath: string | null
}
```

## 3. 탭바 배치 — 두 줄

```
┌──────────────────────────────────────────┐
│ ⬤⬤⬤  [git-gui ×][api-server ×][+]      │ ← 탭바 = 타이틀바 (드래그·신호등)
├──────────────────────────────────────────┤
│ git-gui ▾ │ main │ 병합 가져오기 …        │ ← 지금 헤더 그대로
├──────────────────────────────────────────┤
│  변경 │ Diff │ 커밋 히스토리              │
└──────────────────────────────────────────┘
```

**타이틀바 구실이 헤더에서 탭바로 옮겨간다.** 지금 `.app__header`가 갖고 있는 세 가지를 그대로 물려받는다(`layout.css:9-27`):
- `padding-left: 80px` — 신호등 자리(전체화면에서는 `body.is-fullscreen`이 접는다)
- `-webkit-app-region: drag` + 인터랙티브 요소 공용 `no-drag`
- `trafficLightPosition.y`는 **탭바 높이 기준으로 다시 잰다**(지금은 헤더 58px 기준 y=22)

헤더는 그 아래로 내려가 **아무것도 안 바뀐다** — E7k 반응형·저장소 전환기·버튼 일곱이 그대로다. 대가는 세로 공간 한 줄이다.

**저장소 전환기(E15a)는 남긴다.** 탭바가 "열려 있는 것들"을 보여 준다면 전환기는 "최근에 열었던 것들"을 보여 준다 — 역할이 다르다. 전환기에서 고르면 **지금 탭이 갈아탄다**(새 탭이 아니다). 새 탭은 `+`와 `⌘T`다.

**단, 전환기도 중복 차단을 지나간다** — 고른 저장소가 **다른 탭에 이미 열려 있으면** 지금 탭을 갈아타지 않고 그 탭을 활성화한다. 안 그러면 같은 저장소가 두 탭에 생겨 §5의 규칙이 무너진다. 즉 규칙은 하나다: **"이 저장소를 보여 달라"는 요청은 전부 한 곳을 지나고, 이미 있으면 거기로 데려간다."**

  | 요청 | 이미 열려 있으면 | 아니면 |
  | --- | --- | --- |
  | 전환기 클릭 | 그 탭 활성화 | 지금 탭이 갈아탄다 |
  | `⌘T` → 최근 목록 · "새 탭에서 열기" | 그 탭 활성화 | 새 탭 |
  | ⌥클릭 · "새 창에서 열기" | 그 **창**을 앞으로 + 그 탭 활성화 | 새 창 |

## 4. 레이아웃은 창 단위로 동기화

탭이 각자 webContents라 **아무것도 안 하면 자연히 탭별**이 된다. 창 단위로 만들려면 배선이 하나 는다:

1. `settings:set`이 창별 필드(`WindowLayout`)를 받으면 → 레지스트리의 **창** layout을 갱신
2. → **그 창의 다른 모든 탭에** push (`settings:layout-changed`)
3. 렌더러가 그 push를 받아 자기 레이아웃 상태를 갱신

3번이 **새로 필요한 능력**이다. 오늘 렌더러는 `settingsApi.initial`을 마운트 시 한 번 읽을 뿐이고(`App.tsx:157`·`:158`·`:202`·`:267`·`:268`의 다섯 `useState`), 바깥에서 오는 갱신을 받을 길이 없다.

**메아리를 막아야 한다** — push를 받아 상태를 바꾸면 그 변경이 다시 `settings:set`을 부르지 않아야 한다. push 적용 경로와 사용자 조작 경로를 갈라야 하고, 그 구분이 없으면 두 탭이 무한히 서로를 갱신한다.

숨은 탭도 push를 받아 두므로 나중에 켜도 이미 맞아 있다.

## 5. 탭 수명

| 동작 | 결정 |
| --- | --- |
| `⌘T` · 탭바 `+` | 빈 탭(`RepoPicker`, 최근 목록 포함 — E15b가 붙였다) |
| `⌘W` | 탭 닫기. **마지막 탭이면 창이 닫힌다** |
| `⌘N` | 새 **창** — E15b가 만든 기억을 깨지 않는다 |
| `⌃Tab` · `⌘⇧[`/`⌘⇧]` · `⌘1..9` | 탭 전환 |
| 탭 우클릭 | 닫기 · 다른 탭 모두 닫기 · **새 창으로 분리** |
| 중복 차단 | **모든 창의 모든 탭**을 훑는다. 이미 있으면 그 탭을 활성화하고 그 창을 앞으로 |
| 터미널 상한 | **탭마다 8개** — `sender` 기준이라 자동으로 그렇게 된다 |

E15b의 진입점 넷(전환기 ⌥클릭·우클릭·⌘N·워크트리)은 그대로 두고 **"새 탭에서 열기"가 짝으로 붙는다.**

**탭 라벨**은 저장소 이름(마지막 폴더)이다. 같은 이름이 둘이면 구분이 필요한데, `worktree-label.ts`의 `uniqueNames`가 E7j에서 정확히 이 문제를 풀었다 — 재사용을 확인한다.

## 6. 복원

E15b의 `windows` 배열이 한 겹 깊어진다:

```ts
windows?: Array<{
  tabs: Array<{ repoPath: string | null }>
  activeTab: number
  layout: WindowLayout
}>
```

`sanitizePersistedSettings`가 방어한다 — E15b와 같은 이유로, 이 값은 사람이 편집할 수 있는 디스크 파일에서 오고 `repoPath`가 **뷰를 만드는 인자**가 된다. E15b가 배운 것을 그대로 가져온다: 배열 원소가 `typeof === 'object'`를 통과하므로 `!Array.isArray(entry)`가 필요하고, **타입이 틀린 `repoPath`는 `null`로 낮추지 말고 버린다**(낮추면 유령 빈 탭이 생기고 종료 시 다시 저장돼 고착된다).

**E15b의 영속 규칙을 그대로 잇는다**: 레지스트리가 바뀔 때마다 영속(레이아웃은 250ms 디바운스), 종료 시 빈 목록으로 덮어쓰지 않기, `before-quit` 이후 목록 얼리기. 셋 다 E15b 리뷰가 실측으로 찾은 것이라 다시 발견하지 않는다.

## 7. 드래그 떼어내기

**이 에픽의 두 번째 미지수다.** 탭바를 렌더러가 그리는데 드래그는 창 밖으로 나가야 한다.

설계 방향: 렌더러가 드래그 시작을 main에 알리고 → main이 `screen.getCursorScreenPoint()`(`electron.d.ts:11201`)로 커서를 좇으며 드롭 대상을 정하고 → 놓는 순간 뷰를 옮긴다. **뷰가 온전한 webContents라 상태를 직렬화할 필요가 없다** — `contentView.removeChildView` 후 다른 창의 `addChildView`다.

**확인해야 할 것**: 버튼을 누른 채 커서가 창 밖으로 나갔을 때 **원래 렌더러가 `pointerup`을 계속 받는지**. 안 받으면 드래그 종료를 감지할 다른 길(main의 폴링 + 전역 마우스 상태)이 필요하다. 이건 실측으로만 알 수 있다.

떨어뜨릴 자리 미리보기도 직접 그려야 한다.

## 8. 관문 — 이 에픽의 진짜 위험

**E2E 150건이 전부 `BrowserWindow` 하나를 전제로 짜여 있고 `firstWindow()`가 155곳이다.**

`BaseWindow` + `WebContentsView`로 바꾸면 Playwright가 앱을 **여전히 몰 수 있는지**가 미지수다. `_electron`이 `WebContentsView`의 webContents를 page로 잡아 주는지, `firstWindow()`가 무엇을 돌려주는지, `app.windows()`가 뷰를 세는지 — **API 문서로 알 수 없고 돌려 봐야 안다.**

E15b Task 1과 같은 종류의 위험이지만 **규모가 훨씬 크다**: 그때는 "두 창이 잡히는가"였고 이번엔 "기존 150건이 아직 도는가"다.

**그래서 첫 태스크는 창 하나·탭 하나짜리 `BaseWindow` 마이그레이션만 하고 기존 150건이 그대로 도는지 확인하는 것이다.** 안 되면 거기서 멈추고 보고한다 — 나머지 전부가 그 위에 선다.

## 9. 이 스펙은 두 에픽으로 나눠야 한다

> **컨트롤러 판단 — 사용자 확인이 필요하다.**

이 문서가 담은 것은 한 에픽 크기가 아니다:

**E15c — 탭** (이 문서의 §2~6, §8)
창 모델 마이그레이션 · 탭바 · 탭 CRUD · 창 단위 레이아웃 동기화 · 복원 · 중복 차단. **탭이 동작하는 상태로 끝난다.**

**E15d — 떼어내기** (§7)
드래그로 탭을 새 창으로 · 다른 창의 탭바로 이동 · 창 합치기.

**나누는 이유**: §8의 관문이 E15c 첫 태스크에서 열리고, 그게 실패하면 §7은 논의할 것도 없다. 그리고 §7은 그 자체로 미지수가 따로 있다(창 밖 `pointerup`). 한 에픽에 묶으면 **관문이 둘인 에픽**이 되고, 리뷰가 감당하기 어려워진다.

**나눠도 사용자가 요구한 것은 전부 만든다** — 순서만 정하는 것이다. E15a→E15b가 같은 방식이었다.

## 10. 이 에픽에서 하지 않는 것

- **Windows/Linux 탭바 외형 미세 조정** — 구조는 플랫폼 공통이지만 신호등이 없는 플랫폼의 여백은 나중에 본다
- **탭 고정(pin)·탭 검색·세션 저장** — 브라우저에는 있지만 지금 필요가 없다
- E15b에서 넘어온 후속: 복원의 직렬 `stat`(죽은 네트워크 마운트 하나가 첫 창을 막는다) · ⌥클릭의 키보드 대응 부재 · 중복 차단이 같은 대상일 때 무반응 · 크래시한 렌더러의 뷰 잔류 · E15a의 `headInfos` 캐시 만료

## 11. 성공 기준

- 한 창에서 `⌘T`·`+`로 저장소를 여러 개 열고 탭으로 오간다
- **기존 E2E 150건이 그대로 돈다** (관문)
- 탭바가 타이틀바를 겸하고 신호등이 그 안에 세로 중앙으로 앉는다
- 한 탭에서 사이드를 접으면 **같은 창의 다른 탭도** 접히고, 다른 창은 안 접힌다
- 같은 저장소를 다시 열면 새 탭이 안 생기고 그 탭이 활성화된다
- 껐다 켜면 창과 그 안의 탭들이 순서·활성 탭까지 돌아온다
- 게이트: lint 0 errors · typecheck 6/6 · `pnpm test` 672 이상 · e2e 150 이상
