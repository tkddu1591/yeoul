# E15e — 크래시 탭 처리 (E15c 리뷰 I-2)

> E15c 리뷰가 실측으로 재현한 것: 크래시한 렌더러는 `destroyed`가 아니라 수명 배선이
> 안 돌고 레지스트리·탭바·contentView에 잔류한다. **활성 탭이 크래시하면 탭바도
> 단축키도 그 죽은 렌더러 안이라 창 전체가 인질** — 살아 있는 탭으로 갈 방법이 없고,
> 유일한 출구(창 닫기)는 산 탭까지 잃는다. 중복 판정도 크래시 탭을 "이미 열림"으로
> 보고 사용자를 죽은 뷰로 데려간다. E15b 시절 손실 단위가 저장소 하나였다면 이제 N탭이다.

## 1. 설계 — 선택지가 제약으로 강제된다

**탭바는 각 뷰가 자기 안에 그린다**(E15c 결정 — `firstWindow()` 155곳 보존). 따라서
크래시 복구의 주체는 렌더러가 될 수 없고 **main뿐이다.** 죽은 webContents에는 아무것도
그릴 수 없으므로 "크래시 화면"도 불가능하다 — 남는 수단은 셋뿐이다: 전환·표시·reload.

`view.webContents.on('render-process-gone')`에서 main이:

1. **레지스트리에 `crashed` 표시** → `tabs:changed` push — 산 형제들의 탭바에 죽음 표시가 뜬다.
2. **크래시 탭이 활성이고 산 형제가 있으면** → 산 이웃으로 활성 전환(오른쪽 우선 —
   `removeTab` 승계와 같은 규칙). **이게 인질 해방이다.**
3. **크래시 탭이 유일한 탭이면** → `reload()` — 단 **연속 자동 재시동은 상한(3회)까지만**
   (리뷰 I-1: "로드하면 반드시 죽는" 렌더러면 reload 완료가 곧장 다음 크래시를 불러 무한
   루프가 된다 — 실측 15초에 크래시 157회). 연속의 판정은 시각으로 한다: 로드 완료 후
   10초를 살면 다음 크래시는 새 사건(1부터). 상한을 넘기면 크래시 표시를 남긴 채 정지한다
   — 유일 탭은 죽은 뷰가 선 채 남는다(§3이 감수한 "수동 클릭 복구만"의 극단 — 브라우저의
   sad-tab과 달리 죽은 뷰에 안내를 그릴 수 없고, 루프보다는 정지가 낫다).

**복구 경로**: 산 형제의 탭바에서 죽은 탭을 클릭(`tabs:activate`)하면 main이 `reload()`
후 활성화한다. `did-finish-load`에서 `crashed` 해제 → push로 죽음 표시가 걷힌다.

**중복 판정 정합**: `tabs:show-existing`·`window:open`의 reveal이 크래시 탭을 만나면
reveal에 reload를 얹는다 — 사용자를 죽은 뷰로 데려가지 않는다.

## 2. 계약서

`TabInfo`에 `crashed?: boolean` (없으면 산 것 — 기존 소비처 무변). 새 IPC 없음 —
`tabs:activate`가 reload를 겸하고, 표시는 기존 `tabs:changed`로 흐른다.

## 3. 하지 않는 것

- 크래시 원인 표시·로그 수집 (`details.reason`은 main 로그만)
- 무한 자동 재시도 (자동 재시동은 §1의 연속 상한까지만 — 앱의 추측은 유한해야 한다.
  수동 클릭 복구(`tabs:activate`)·reveal은 사용자의 의지라 상한과 무관하게 언제나 reload)
- 세션 상태 복원 (reload는 그 저장소를 처음부터 다시 연다 — E15a의 `repo:initial-path` 경로)

## 4. 성공 기준

- 활성 탭이 크래시해도 창이 인질이 되지 않는다 — 산 이웃이 즉시 활성
- 산 탭의 탭바에 죽음 표시, 클릭하면 되살아난다
- 유일한 탭 크래시는 자동 재시동 — 단 연속 상한까지: 크래시-온-로드가 무한 reload 루프가 되지 않는다
- reveal이 죽은 뷰로 데려가지 않는다
